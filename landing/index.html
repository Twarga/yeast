For AI agents.

corridor one

Everything an agent touches returns the same shape of answer. yeast.v1 is frozen; yeast.v2 only adds. Tools arrive through yeast mcp over stdio or the daemon's /mcp endpoint — and .yeast/agent-policy.yaml, not client annotations, decides what is allowed.

--json

Frozen JSON, every command

Every verb answers in a versioned envelope: schema_version: yeast.v2, stable fields, documented error codes.

--events

Event streams

Lifecycle workflows stream JSON Lines events — boot, provision, restore, down — so agents watch progress, not exit codes.

yeast mcp

A native MCP server

Speaks MCP over stdio for one project, or Streamable HTTP on the daemon. Same tools, same JSON.

yeast daemon

A daemon when you want one

Local HTTP + SSE API for every service action, plus a WebSocket VNC proxy so a UI can watch the screen.

pkg/yeast

A Go SDK

The public pkg/yeast package drives the same engine — for tools that would rather link than shell out.

.yeast/agent-policy.yaml

Policy the server enforces

Allowed and denied tools, exec timeouts, auto-snapshot-before-exec — decided inside Yeast, not by the client.

audit log

Receipts, append-only

Every action lands in an append-only audit log. What the agent did is written down — not up for debate.

egress.mode

Network on a leash

open, offline, or allowlist through a Yeast proxy that logs every allowed and refused domain. Fails closed.

# .yeast/agent-policy.yaml — enforced server-side by yeast mcp
allow: [vm_up, vm_down, vm_snapshot, vm_restore, vm_exec, vm_screenshot]
deny:  [vm_destroy]
snapshot_before_exec: true
max_exec_timeout: 2m

enforced by yeast mcp — client annotations never override server policy

For Linux labs.

corridor two

A lab is a machine you can see, poke, and rewind. Boot a desktop with UEFI and a virgl GPU, watch it over VNC, drive it through QMP — then snapshot, fork, and export the whole thing.

display: vnc · gpu: virgl · uefi

A real display

Graphical desktops over VNC with virtio-gpu/virgl acceleration and UEFI firmware. It is a computer, not a container.

yeast screenshot web -o vm.png

Screenshots on demand

QMP screendump grabs the framebuffer as PNG — proof of what the guest actually drew.

yeast input web --key meta_l+ret · --text "…"

Hands you can script

Send keys and typed text through QMP. Drive an installer, press enter, paste a command — no SSH required.

virtiofs / 9p

Shared folders

Mount a host directory into the guest with virtiofs or 9p. Your files, both sides of the wall.

yeast snapshot web golden

Live snapshots

RAM and disk captured while the machine keeps running. Restore lands in about two seconds.

yeast fork web --count 3

Fork the lab

Parallel copies of one machine — same state, three benches. Run the experiment side by side.

yeast export

Take it with you

Export images as qcow2, a plain rootfs, or a bootable ISO. The lab leaves the nest intact.

yeast run --rm ubuntu-24.04 -- bash -lc 'make test'

Use and throw away

Boot, run the command, print the result, delete the machine. Ephemeral by flag, not by faith.

The trick everyone asks about.

Snapshots in Yeast are live — RAM and disk, taken while the machine keeps running. Restore is the point of the exercise: it puts the machine back in about two seconds. Fork is the other half: one good state becomes many machines. Try it:

  1. yeast snapshot web goldenlive — ram + disk, no downtime
  2. break the guest however you likedelete the config, corrupt the service — go on
  3. yeast restore web goldenback in about two seconds
  4. yeast fork web --count 3one golden state, three machines

What it needs. What it won't do.

Hand-made, not magic. Yeast asks for a few things up front, and it says no plainly.

✓ needs

  • a Linux host with /dev/kvm — WSL2 works in beta
  • QEMU installed — yeast drives it, it doesn't replace it
  • rootless — no sudo, no system daemon
  • the RAM and disk you actually assign, and not much more

✗ won't do

  • no cloud control plane — your machines stay yours
  • no Windows-guest focus — Linux guests are home turf
  • and no pretending a broken host is fine:
$ yeast doctor
✓ /dev/kvm            readable + writable
✓ qemu-system-x86_64  found
✗ vt-x in bios        off — enable it, then come back

doctor tells you the truth before you waste an afternoon.

A taste of the verbs.

$yeast up                                            # everything in yeast.yaml, running
$yeast snapshot web golden                          # live ram+disk, vm keeps running
$yeast restore web golden                           # back in about two seconds
$yeast fork web --count 3                           # three copies for parallel work
$yeast screenshot web -o vm.png                     # framebuffer over qmp
$yeast mcp                                          # tools for your agent, over stdio
$yeast run --rm ubuntu-24.04 -- bash -lc 'make test' # use and throw away

every verb also speaks --json and --events — the same answer, for a human or a machine.
